# Deviations from the specification

The implementing agent records here every place where the implementation differs from ARCHITECTURE.md or the docs, for example because the DeepStream 9.1 public headers or behaviour differ from what the spec assumed.

| # | Date | Spec reference | Deviation | Reason / evidence (header path, doc link, test) |
|---|---|---|---|---|
| 1 | 2026-11-20 | docs/LICENSING.md §7 ("SPDX headers: every source/config/script file") | JSON files cannot hold comments: `schemas/*.json` carry `"$comment": "SPDX-License-Identifier: Apache-2.0"`; golden test data under `tests/golden/` and `labels.txt` files are exempt from the header check. Docs/config files need the SPDX line only; code files also need a copyright line. | JSON spec (RFC 8259) has no comment syntax; `$comment` is a JSON Schema 2020-12 keyword. Rules in `tools/ci/check_spdx.py`. |
| 2 | 2026-11-20 | CLAUDE.md "Known traps" (`msgapi_init_early`, `msgapi_report_error_and_cleanup`, `g_nvds_last_error_message`, `appCtx->last_error` "not in public DeepStream"); ARCHITECTURE §3.2 | These **do exist** in public DeepStream 9.1. Perceptra still does not call them (design decision kept: startup errors go to logs, later `/startup`). | `sources/apps/sample_apps/deepstream-app/deepstream_app.h` (msgapi_*, `last_error`), `apps-common/includes/deepstream_common.h:33` (weak `g_nvds_last_error_message`) in `deepstream:9.1-samples-multiarch`. |
| 3 | 2026-11-20 | CLAUDE.md: verify `get_sensor_info` / `NvDsSensorInfo` | Both exist in DS 9.1 (`deepstream_app.h:317`, `gst-nvdscommonconfig.h:88`; fields `source_id, uri, sensor_id, sensor_name`), so the REST stream-add fallback mapping is not needed. Note: `get_sensor_info` is an unlocked `GHashTable` lookup; M4 must account for concurrent REST add/remove. | DS 9.1 headers. |
| 4 | 2026-11-20 | IMPLEMENTATION_PLAN M1 Dockerfile (build deps) | The `-samples-` image has the CUDA runtime but no CUDA headers. The build stage installs `cuda-cudart-dev-X-Y` and `cuda-crt-X-Y` pinned to the in-image cudart version (CUDA 13 moved `crt/host_defines.h` to `cuda-crt`). Build stage only; runtime image unchanged. | `find / -name cuda_runtime_api.h` empty in the base image; NVIDIA CUDA apt repo. |
| 5 | 2026-11-20 | CLAUDE.md Makefile traps; RT-CV Makefile | Dropped `-lcuda` (libcuda.so is injected by the NVIDIA runtime, not present at build time; nothing we compile needs it at link), `-lcrypto`, `-lnvds_batch_jpegenc`, `frame_dump.cpp`, `DS_VERSION_MAJOR/MINOR` (unused by any source in DS 9.1; `nvds_version.h` has the real version). Did not compile DS `nvds_utils.cpp` (needs OpenSSL `SHA256`, not on the licence allow-list); `src/app/ds_compat.c` provides our own `nvds_get_hostname_with_ip()` (only used by the unused msgapi error path). | Link errors observed in `deepstream:9.1-samples-multiarch`; `grep -rn DS_VERSION_ sources/` empty. |
| 6 | 2026-11-20 | IMPLEMENTATION_PLAN M1 "Force TCP for RTSP" (RT-CV sets `multi_source_config[j].select_rtp_protocol`) | With `nvmultiurisrcbin` there are 0 static sources, so RT-CV's loop is a no-op for REST-added streams. Perceptra also sets `source_attr_all_config.select_rtp_protocol = 0x04`, which `create_nvmultiurisrcbin_bin` applies to every added source. | `apps-common/src/deepstream_source_bin.c` (`select-rtp-protocol` set from the source-attr-all config); `gst-inspect-1.0 nvmultiurisrcbin`. |
| 7 | 2026-11-20 | IMPLEMENTATION_PLAN M1 "SIGINT/SIGTERM → EOS" | Signals only quit the main loop; EOS is sent by DeepStream's `destroy_pipeline()`, which sends EOS, drains the bus until EOS and sets NULL. RT-CV handled only SIGINT via `sigaction`; Perceptra uses `g_unix_signal_add` for both. | `deepstream_app.c` `destroy_pipeline()` (DS 9.1). |
| 8 | 2026-11-20 | IMPLEMENTATION_PLAN M1 "SIGTERM exits 0"; ARCHITECTURE §4.1 (EOS, set NULL, destroy) | **DeepStream 9.1 bug workaround.** Once any stream has been added to `nvmultiurisrcbin` (still active or already removed), `destroy_pipeline()` blocks forever while setting the pipeline to NULL. `perceptra` bounds teardown with a watchdog (`--shutdown-timeout`, default 8 s, below Docker's 10 s stop grace) that logs `event=shutdown_timeout` at warn level and `_exit()`s with the already-decided exit code (0 after SIGTERM). From M4 on, the publisher must be flushed **before** pipeline teardown. With 0 streams ever added, teardown completes normally (~3 s). Revisit on each DeepStream upgrade. | gdb backtrace of the main thread: `destroy_pipeline` (deepstream_app.c:2513) → `gst_element_set_state(NULL)` → `libnvdsgst_multistream.so` → `gst_pad_stop_task`; the muxer loop keeps logging "No Sources found at the input of muxer. Waiting for sources." Not fixed by clearing `drop-pipeline-eos` before teardown. Related reports: DeepStream forum threads on `set_state(NULL)` hangs with nvmultiurisrcbin in 9.1. |
| 9 | 2026-11-20 | — (evaluated alternative) | The new muxer (`USE_NEW_NVSTREAMMUX=yes`) shuts down cleanly but is **not used**: with the M1 config the whole pipeline EOS'd and the app exited as soon as a file stream ended, and it has documented gaps (single output resolution, deepstream-server unsupported). The classic `nvstreammux` stays the default. | Manual test 2026-11-20 (`Received EOS. Exiting ...` after file EOS); DS 9.0/9.1 release notes. |
| 10 | 2026-11-20 | docs/PARSERS.md "DeepStream adapter" (`NvDsInferParseObjectInfo{classId, left, top, width, height, detectionConfidence}`) | In DS 9.1 `NvDsInferParseObjectInfo` is a typedef of `NvDsInferObjectDetectionInfo`, which adds `rotation_angle` (OBB). The adapter zero-initialises every object (`rotation_angle = 0`, axis-aligned), drops class ids `>= numClassesConfigured` and clamps confidence to [0, 1], as the nvinfer contract requires. | `sources/includes/nvdsinfer.h:148-176`, `nvdsinfer_custom_impl.h:185-197` (DS 9.1). |
| 11 | 2026-11-20 | docs/PARSERS.md core types (`TensorView{const float* data, ...}`), families table | Clarifications, no contract change: (a) `TensorView` stays float-only; the adapter converts INT32/INT64 layers (EfficientNMS `num_dets`/`classes`) into per-thread float buffers, other types (e.g. HALF) fail with a one-time error. (b) Leading 1-sized dims are dropped only while the tensor has more dims than the family's rank, so a real single row `[1, 6]` is kept. (c) DETR `has_background_class`: the background is the **last** logit column. (d) `yolo_raw` expects `4 + C` channels without objectness (YOLOv5-style `5 + C` is not supported). (e) Without `PERCEPTRA_PARSER_CONFIG` the adapter warns once and uses family defaults, output order and nvinfer's class count; a `parser.ini` whose `family` differs from the called function is an error. (f) `parser.ini` is parsed strictly (unknown keys/sections are errors). | `src/parsers/core/*.cpp`, `src/parsers/ds_adapter.cpp`, tests in `src/parsers/tests/`. |
| 12 | 2026-11-20 | docs/TESTING.md (parser tests) | Parser tests run under ASan + UBSan. Two DS-image quirks are handled in the build: the image sets `LD_PRELOAD` (libgomp, libGLdispatch), which ASan refuses to run behind, so `make test*` runs the binaries with `env -u LD_PRELOAD`; TensorRT headers include `cuda_runtime_api.h`, so `libperceptra_parsers.so` is built in the Dockerfile build stage (CUDA dev headers, deviation #4) where `make test` also runs. | `docker run ... deepstream:9.1-samples-multiarch -c 'echo $LD_PRELOAD'`; `NvInferRuntimeBase.h:24`. |
